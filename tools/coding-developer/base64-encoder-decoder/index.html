      In-depth guide
      
What Base64 encoding actually does

      
Base64 represents binary data using 64 printable ASCII characters: A–Z, a–z, 0–9, plus and slash. Every three input bytes become four output characters, which is why encoded data is roughly one third larger than the original. The format exists because many systems were designed to carry text and cannot safely transport raw bytes. Email attachments, data URLs, JSON fields and authentication headers all rely on this kind of text-safe representation. An encoder does not interpret the content. It simply maps bytes to characters according to a fixed table, optionally adds padding and returns a string that can travel through text-only channels without being mistaken for control characters.

      
Why UTF-8 matters for accents and emoji

      
Text is not stored as characters inside a computer; it is stored as bytes. This tool converts your text to UTF-8 first, then encodes those bytes. That detail matters for accented letters, non-Latin scripts and emoji. The word Café contains a two-byte é in UTF-8, and an emoji can occupy four bytes, so their Base64 output will not match a naive character-by-character calculation. When decoding, the tool reverses the process and validates the result as UTF-8. If the bytes are not valid UTF-8 text, it reports an error rather than showing replacement symbols. This strict behaviour helps you notice when you are decoding a file, image or encrypted value instead of text.

      
Standard Base64, URL-safe Base64 and padding

      
Standard Base64 uses plus and slash, but those characters have special meanings in URLs and can be altered by form handling. URL-safe Base64 replaces plus with a hyphen and slash with an underscore, making the result safer to place in a query string or filename. Padding uses equals signs to fill the final group to four characters. Some systems keep the padding; others strip it. This decoder accepts both alphabets and can restore missing padding automatically, so you can paste a value copied from a JWT, a data URL or an API response without editing it first. The encoder's URL-safe option removes padding as well, matching the common token convention.

      
Common practical uses

      
Base64 appears in more places than many developers expect. Data URLs embed small images, fonts and icons directly in CSS or HTML. Email uses MIME encoding for attachments. JSON APIs sometimes carry binary blobs as strings. JWTs encode their header and payload segments with URL-safe Base64, although the result is not encrypted. Basic authentication headers combine a username and password with Base64. Log files and debugging tools may show encoded values that need a quick decode. A browser-based encoder is convenient for these checks because it needs no install and leaves nothing on a server. For round-trip work, use the swap button to send the output back through the opposite direction.

      
What Base64 is not

      
Base64 is not encryption, compression or a security control. Anyone who has the string can decode it with a few lines of code, so it must never be used to hide passwords, API keys or private records. It also adds size rather than reducing it. If you need to protect data, use encryption and key management designed for that purpose. If you need to shrink data, use compression. Use Base64 only when a text-only channel requires a safe representation of bytes. Remember that clipboard history, browser extensions and shared screens can expose anything you paste, even though this tool processes locally. Decode only data you trust, and validate the result before feeding it into another system.

  





  

    

      
Frequently asked questions

      

  Is Base64 a form of encryption?
  
No. Base64 is a reversible text representation of bytes. Anyone with the string can decode it. Never use Base64 to protect passwords, API keys or private records; use proper encryption and key management instead.



  Why is the encoded output longer than the input?
  
Base64 represents every three bytes with four ASCII characters, so the encoded form is about one third larger. UTF-8 text can also use multiple bytes per character, which affects the final length.



  Does the tool support Unicode and emoji?
  
Yes. Text is converted to UTF-8 bytes before encoding, so accented letters, non-Latin scripts and emoji round-trip correctly. Decoding validates that the bytes are valid UTF-8 text.



  What is URL-safe Base64?
  
It replaces plus with a hyphen and slash with an underscore, and usually removes equals-sign padding. This makes the value safer inside URLs, filenames and JSON Web Tokens. The decoder accepts both standard and URL-safe alphabets.



  Why do I get an error when decoding?
  
The value may contain characters outside the Base64 alphabet, have an impossible length, or represent binary data that is not valid UTF-8 text. Check that you copied the complete value and that it is text rather than an image or encrypted file.
